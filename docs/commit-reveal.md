# Commit-Reveal Voting

## Overview

Commit-reveal is an optional governor-wide voting mode. When it is enabled for a proposal, voting is split into two consecutive windows:

1. **Commit phase** — a voter submits a hash of their intended vote, but not the vote itself.
2. **Reveal phase** — the voter submits the preimage. The governor recomputes the hash and, if it matches, applies the vote to the tally.

The implementation lives in `contracts/governor/src/commit_reveal.rs`, with the public entrypoints in `contracts/governor/src/lib.rs`. The SDK exposes the corresponding helpers on `GovernorClient` (`sdk/src/governor/commitReveal.ts`).

Commit-reveal is **disabled by default**. It is controlled by two governor settings, `use_commit_reveal` and `commit_phase_fraction`, and the split is snapshotted when each proposal is created. Changing the settings later does not change an in-flight proposal.

## Threat model

### What it protects against

- **Last-block vote copying and bandwagoning.** While the commit window is open, observers see only fixed-size commitment hashes. They cannot tell whether a voter supports, opposes, or abstains from a proposal, so they cannot copy a late leader or react to the emerging tally.
- **Conditional bribery.** A briber cannot verify a voter's choice before the reveal window opens, because the commitment does not disclose `support`. A payout conditioned on a particular vote direction cannot be checked from the commitment alone.

Direct `cast_vote` and `cast_vote_with_reason` are rejected for commit-reveal proposals. Otherwise, a voter could bypass the hidden commitment and defeat both properties.

### What it does not protect against

- Commit-reveal is **not full ballot secrecy**. A `VoteCommitted` event reveals which address participated and when. Once the reveal phase starts, every revealed vote and its weight become public.
- The preimage is protected by a random 128-bit `weight_seed` and a random 256-bit salt generated by the SDK, but the scheme is only a salted SHA-256 hash. It does not provide encryption, zero-knowledge proofs, or coercion resistance after the fact.
- There is **no forced reveal, bond, or slashing**. A voter who never reveals simply does not have their vote counted.
- Vote weight is still computed from voting power at the proposal's `start_ledger` snapshot. `weight_seed` is a blinding value in the hash; it does not scale or encode voting power.
- The reveal deadline is the proposal's normal `end_ledger`. There is no separate grace window after reveal closes, so voters must submit the reveal transaction before voting ends.

## Phase timing

`update_config` accepts two settings in `GovernorSettings`:

| Setting                  | Type   | Default | Meaning                                                          |
| ------------------------ | ------ | ------- | ---------------------------------------------------------------- |
| `use_commit_reveal`      | `bool` | `false` | Enable the two-phase flow for **new** proposals                  |
| `commit_phase_fraction`  | `u32`  | `5,000` | Share of `voting_period` given to commit, in basis points (50%)  |

`update_config` requires the governor contract's own authorization (governance action) and rejects a fraction of `0` or `>= 10,000`, so both phases have room to exist.

At proposal creation the contract snapshots:

```text
voting_period   = end_ledger - start_ledger
commit_ledgers  = floor(voting_period * commit_phase_fraction / 10_000)
commit_deadline = start_ledger + commit_ledgers
reveal_deadline = end_ledger
```

The deadlines are stored per proposal in `CommitDeadline` and `RevealDeadline`, and a `CommitPhaseStarted` event publishes them. Later configuration changes do not affect proposals that already have deadlines.

The authoritative contract windows are:

- **Commit allowed:** `start_ledger <= current_ledger <= commit_deadline`
- **Reveal allowed:** `commit_deadline < current_ledger <= reveal_deadline`

For example, with `start_ledger = 11`, `end_ledger = 111`, and the default 5,000 bps fraction, `commit_deadline = 61`. Commits are accepted through ledger 61; reveals are accepted from ledger 62 through ledger 111.

## The commitment preimage

The SDK's `generateCommitment()` and the contract's `compute_commitment()` must produce the same 32-byte digest. The exact preimage is:

```text
sha256(
  proposal_id_le   // u64, 8 bytes, little-endian
  || support_u8    // 1 byte
  || weight_seed_le// u128, 16 bytes, little-endian
  || salt          // exactly 32 raw bytes
)
```

| Field          | Encoding                           | Notes                                      |
| -------------- | ---------------------------------- | ------------------------------------------ |
| `proposal_id`  | `u64` little-endian, 8 bytes       | Same proposal ID used in both transactions |
| `support`      | `u8`, 1 byte                       | `Against = 0`, `For = 1`, `Abstain = 2`    |
| `weight_seed`  | `u128` little-endian, 16 bytes     | Random blinding value, not voting weight   |
| `salt`         | 32 raw bytes                       | Random blinding value                      |

Golden test vector: `proposalId = 42n`, `support = For`, `weightSeed = 123456789n`, and a salt of 32 `0xAB` bytes produce:

```text
ddc09c2c64223bb2cd359e5a6608c9b6ac1dfc95c40cc94cbd632fbe4d53188f
```

The SDK's `generateCommitment()` uses Node's synchronous crypto module. There is no browser-compatible synchronous SHA-256 helper in this SDK, so commitment generation must run in a Node environment (server, script, or test harness) and the resulting commitment and preimage values must be passed to the client.

## Contract entrypoints

| Entrypoint                                                                 | Authorization | Purpose                                                       |
| -------------------------------------------------------------------------- | ------------- | ------------------------------------------------------------- |
| `commit_vote(voter, proposal_id, commitment)`                              | `voter`       | Store a 32-byte commitment during the commit window           |
| `reveal_vote(voter, proposal_id, support, weight_seed, salt)`              | `voter`       | Verify the preimage and apply the vote during the reveal window |
| `get_commit_deadline(proposal_id)`                                         | read-only     | Read the snapshotted commit deadline                          |
| `get_reveal_deadline(proposal_id)`                                         | read-only     | Read the snapshotted reveal deadline                          |
| `has_committed(proposal_id, voter)`                                        | read-only     | Check whether an address committed                            |

Relevant errors:

| Error                     | Cause                                                              |
| ------------------------- | ------------------------------------------------------------------ |
| `CommitRevealNotEnabled`  | Proposal has no snapshotted commit/reveal deadlines                |
| `CommitPhaseEnded`        | `commit_vote` called after `commit_deadline`                        |
| `RevealPhaseNotStarted`   | `reveal_vote` called at or before `commit_deadline`                 |
| `RevealPhaseEnded`        | `reveal_vote` called after `reveal_deadline`                        |
| `NoCommitmentToReveal`    | No stored commitment for this voter and proposal                   |
| `CommitmentMismatch`      | Recomputed hash differs from the stored commitment                 |
| `AlreadyVoted`            | Voter already committed or already cast a revealed vote            |
| `ProposalNotActive`       | Direct `cast_vote` used on a commit-reveal proposal, or bad window |

Events:

- `CommitPhaseStarted(proposal_id, commit_deadline, reveal_deadline)` at proposal creation.
- `VoteCommitted(voter, proposal_id, commitment)` when a commitment is stored.
- `VoteRevealed(voter, proposal_id, support, weight)` when a preimage is accepted and the vote is tallied.

There are no on-chain `get_commit_count` / `get_reveal_count` functions. Counts must be derived from the event stream; the SDK's `getCommitRevealStatus()` makes a best-effort request to `GET /governor/commit-reveal/:proposalId` on the configured indexer and returns `0` values when no indexer URL is configured or the request fails.

## Unrevealed commitments

A commitment that is never revealed:

- contributes nothing to `votes_for`, `votes_against`, or `votes_abstain`;
- leaves `HasVoted` unset for that voter and proposal;
- cannot be revealed after `reveal_deadline` (`RevealPhaseEnded`);
- remains in persistent storage with a TTL of 3,110,400 ledgers, unless extended by other storage activity.

There is no refund or penalty because commit-reveal does not lock a bond. The proposal proceeds on the votes that were actually revealed, so a low reveal rate can cause a proposal to fail quorum even when many addresses committed.

## SDK walkthrough

```typescript
import { GovernorClient, VoteSupport } from "@nebgov/sdk";
import { Keypair } from "@stellar/stellar-sdk";

const client = new GovernorClient({
  governorAddress: process.env.GOVERNOR_ADDRESS!,
  timelockAddress: process.env.TIMELOCK_ADDRESS!,
  votesAddress: process.env.VOTES_ADDRESS!,
  network: "testnet",
  indexerUrl: process.env.INDEXER_URL,
});

const signer = Keypair.fromSecret(process.env.VOTER_SECRET!);
const proposalId = 42n;
const support = VoteSupport.For;

const status = await client.getCommitRevealStatus(proposalId);
if (status.phase !== "commit") {
  throw new Error(`Expected the commit phase, got ${status.phase}`);
}

const { commitment, weightSeed, salt } = client.generateCommitment({
  proposalId,
  support,
});

const commitHash = await client.commitVote(signer, proposalId, commitment);

// Persist these values securely until the reveal phase. Losing either one
// makes the commitment impossible to reveal.
const saved = {
  weightSeed: weightSeed.toString(),
  salt: salt.toString("hex"),
  commitHash,
};

// ... wait until getCommitRevealStatus(proposalId).phase === "reveal" ...

const revealHash = await client.revealVote(signer, {
  proposalId,
  support,
  weightSeed: BigInt(saved.weightSeed),
  salt: Buffer.from(saved.salt, "hex"),
});
```

`commitVote()` and `revealVote()` submit through the SDK's normal retry policy, simulate before broadcasting, wait for confirmation, and return the Stellar transaction hash. Both calls sign with the voter's keypair and require that key's authorization on chain.

Before submitting a reveal, check `getCommitRevealStatus()` again. The phase reported by the SDK is advisory; the contract's ledger checks are the final authority.
